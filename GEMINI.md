# Gemini Project Overview: Go Marketplace

This document provides a technical overview of the **Go Marketplace** project to help you understand the codebase structure, patterns, and technologies used.

## 🚀 Project Overview

**Go Marketplace** is a high-performance e-commerce backend built with Go and the Fiber v2 framework. It follows a clean, feature-based architecture designed for scalability and maintainability.

## 🏗 Architecture & Patterns

The project follows a **Feature-Based Architecture** with a **Rich Domain Model**. Each domain (e.g., `auth`, `order`, `product`, `wallet`, `payment`, `cart`, `user`) is encapsulated in its own package under `internal/core/`.

### Core Layers (per feature)

1. **Handler (`*_handler.go`)**:
   - HTTP layer using [Fiber v2](https://gofiber.io/).
   - Responsible for request parsing, validation (using DTOs), and calling the service layer.
   - Uses `common.NewResponse` for standardized JSON responses.

2. **Service (`*_service.go`)**:
   - Acts as an orchestrator for business processes.
   - Defines the service interface (e.g., `AuthService`) and consumes repository interfaces.
   - Orchestrates data flow between repositories, domain entities, and other services.
   - **Concrete implementations are private structs** (e.g., `authService`, not `AuthService`).

3. **Domain Entity (`domain.go`)**:
   - Contains the core business logic, validation, and status transitions.
   - Encapsulates state-related rules (Rich Domain Model — keep services thin).

4. **Repository (`*_repo.go`)**:
   - Data access layer using [sqlx](https://github.com/jmoiron/sqlx).
   - Implements SQL queries for PostgreSQL.
   - Repository interfaces live in `*_repo.go` alongside implementations.

5. **DTO (`*_dto.go`)**:
   - Defines request and response structures (Data Transfer Objects).
   - Often includes `Validate()` methods for input validation.

6. **Mocks (`mock_*.go`)**:
   - Generated by [mockery](https://github.com/vektra/mockery) using `.mockery.yaml`.
   - Run `make mock` to regenerate. Never edit mock files manually.

### Shared Layers

- `internal/domain/`: Shared data structures (structs with `db` tags) and global error definitions (`errors.go`).
- `internal/common/`: Shared utilities like the `ResponseWrapper`.
- `internal/middleware/`: Custom Fiber middlewares (e.g., JWT authentication).
- `internal/database/`: Database connection setup and migrations.
- `internal/server/`: Router initialization (`routes.go`) and server startup logic.

## 🔑 Key Features & Logic

- **Authentication**: Local email/password and Google OAuth2. Uses a refresh token *family* pattern for secure session rotation.
- **Wallet & Escrow System**: Internal digital wallet with transaction history. Funds move to `pending_balance` on order and are released to merchants on delivery confirmation.
- **Payment System**: Unified interface for internal wallet payments and external providers (e.g., Midtrans) via webhooks. Webhooks use idempotency keys to prevent duplicate processing.
- **Merchant System**: Users can register shops and manage product listings.
- **Product Search**: PostgreSQL full-text search and pgvector for semantic queries.

## 🧪 Testing Strategy

1. **Unit Tests**: Alongside source files (e.g., `auth_service_test.go`, `domain_test.go`). Mocks isolate dependencies.
2. **Integration Tests**: Under `test/integration/`. Uses **Testcontainers** for a real PostgreSQL instance.
   - `test/integration/repo/`: Tests for the repository layer.
   - `test/integration/api/`: Tests for the HTTP/handler layer.
3. **Run tests**: `make test` (unit) or `make test-integration` (full integration suite).

## 💡 Tips for Working on this Codebase

### Architecture Rules
- **Rich Domain Model first**: Before adding logic to a service, ask — does this belong in `domain.go`? Services orchestrate; domains enforce invariants.
- **Private implementations**: Service and repository concrete types should be unexported structs. Only expose their interfaces.
- **Interface naming**: Do not use the `Interface` suffix (e.g., use `AuthService`, not `AuthServiceInterface`).

### Error Handling
- Always use or extend `internal/domain/errors.go` for domain-level errors.
- Wrap errors with context: `fmt.Errorf("methodName: %w", err)`.

### Dependency Injection
- All wiring happens in `cmd/api/main.go` and `internal/server/routes.go`.
- Use `New*` constructors that accept interfaces.
- Use **setter injection** for circular dependencies (e.g., `payment` ↔ `order`).

### Database
- Use `NamedExecContext` for inserts/updates with named parameters.
- Use `GetContext` (single row) / `SelectContext` (multiple rows) for queries.
- Always propagate `context.Context`.
